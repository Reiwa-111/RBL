# Подробный аудит текущего RBL и новой native-реализации

> Историческая справка: разделы про «новый native backend» ниже описывают промежуточный
> прототип v0.2 с генерацией C и компиляцией через GCC/Clang. В текущем дереве этого
> этапа нет: компилятор сразу выдаёт x86-64 ASM для Linux ELF и для нативного Windows PE
> (runtime на C с `__attribute__((sysv_abi))`), GCC на Windows — только драйвер линковки
> и сборка объекта рантайма. Актуальное состояние — `docs/CURRENT_IMPLEMENTATION.md`,
> `docs/ASM_BACKEND.md`, `docs/WINDOWS.md`.

## Что было в архиве

Исходный проект состоит из пяти Rust-модулей:

- `lexer.rs` — лексический анализатор;
- `parser.rs` — рекурсивный спуск и построение AST;
- `ast.rs` — структура AST и описания типов/операторов;
- `interpreter.rs` — интерпретация AST;
- `main.rs` — CLI и связывание всех этапов.

Также в архиве есть `Cargo.toml`, `Cargo.lock` и `test.rbl`.

Старый RBL — именно интерпретатор, а не компилятор: после чтения файла программа каждый запуск проходит через lexer, parser, а затем интерпретатор рекурсивно обходит AST.

## Лексер старой реализации

Поддерживались следующие токены:

`Int`, `Float`, `Str`, `Ident`

Ключевые слова:

`set`, `let`, `func`, `if`, `elif`, `else`, `return`, `true`, `false`, `and`, `or`, `not`, `for`, `in`

Операторы:

`+`, `-`, `*`, `/`, `=`, `==`, `!=`, `<`, `>`, `<=`, `>=`, `!`, `.`, `..`, `..=`

Скобки и разделители:

`{`, `}`, `(`, `)`, `,`

Комментарии — `//` до конца строки.

Числа имеют необычную, но уже фактически утверждённую форму: целые `123` и float вроде `123f`. Обычная десятичная форма `1.25` старым лексером не поддерживается.

Строки не имеют escape-последовательностей: старая реализация просто ищет следующую двойную кавычку.

## Парсер старой реализации

Грамматика сделана ручным рекурсивным спуском.

Приоритеты выражений от слабого к сильному:

`or -> and -> ==/!= -> сравнения -> диапазон -> +/− -> */ -> unary -> primary`

Важная деталь: `and` и `or` здесь являются обычными бинарными операциями AST. Интерпретатор сначала вычисляет левый и правый операнды, а уже потом применяет оператор. Значит, short-circuit семантики нет.

Primary-выражения:

- литералы;
- идентификаторы;
- `(expr)`;
- вызов функции `name(args)`;
- специальные методы `name.method(args)`.

Statements:

- `set name = expr`;
- `let name = expr`;
- `return [expr]`;
- обычное выражение как statement;
- `if / elif / else`;
- `for variable in range`.

## AST

В AST присутствуют:

`Program -> FuncDecl -> Stmt -> Expr`

У `FuncDecl` есть имя, параметры, необязательный return type и тело.

У `Stmt` есть `set`, `let`, `return`, expression, `if`, `for`.

У `Expr` есть int/float/string/bool, идентификатор, unary, binary, function call, method call и range.

Тип `Type` пока представляет собой просто имя `String`. Поэтому это не полноценная статическая type system.

## Интерпретатор старой реализации

Основной runtime-тип:

- `Int(i64)`;
- `Float(f64)`;
- `Str(String)`;
- `Bool(bool)`;
- `Unit`.

Окружение функции:

`HashMap<String, Value>`.

При чтении переменной выполняется lookup по строковому имени и затем clone значения.

При каждом statement интерпретатор вызывает `exec_stmt`, а выражения вычисляет `eval_expr`. Для binary/unary операций создаётся новый `Value`.

### `set`

`set` означает первое объявление.

Ключевая семантика:

1. сначала проверяется, существует ли имя;
2. если существует — сразу ошибка;
3. только потом вычисляется RHS;
4. значение записывается в environment.

То есть:

```rbl
set x = 1
set x = print("RHS")
```

не должно выполнить второй `print`.

### `let`

`let` означает изменение уже существующей переменной.

Порядок другой:

1. сначала вычисляется RHS;
2. затем проверяется существование имени;
3. затем сравнивается runtime-тип старого и нового значения;
4. после этого происходит запись.

Это специально проверяется regression-тестом.

### `if / elif / else`

Условие должно дать `Bool`. Если условие не bool, runtime завершает программу ошибкой.

`elif` проверяются последовательно и только пока предыдущая ветка не сработала.

Блоки не создают отдельные environment: переменная, созданная внутри блока, остаётся в текущем environment.

### `for`

Range должен быть именно AST-узлом `Range`.

`start..end` — верхняя граница не включается.

`start..=end` — включается.

Обе границы должны быть `int`.

Переменная цикла записывается в текущее окружение и после непустого цикла продолжает существовать.

Если цикл пустой, переменная цикла вообще не появляется — это тоже зафиксировано тестами.

### Арифметика

`int` работает только с `int`.

`float` работает только с `float`.

`string` поддерживает только `+`.

`bool` не допускается в арифметике.

Сравнения разрешены для пар `int/int` и `float/float`.

Equality использует `PartialEq` значения, поэтому разные типы равными не становятся.

### Функции

Для user function старая реализация сначала:

1. ищет функцию;
2. проверяет число аргументов;
3. только после этого вычисляет аргументы;
4. проверяет тип каждого аргумента;
5. создаёт новый local environment;
6. вставляет параметры;
7. исполняет body.

Это важно: неправильная арность не должна запускать побочные эффекты внутри аргументов.

Рекурсия уже поддерживается автоматически через рекурсивный вызов интерпретатора.

Return type объявляется в AST, но старый runtime фактически его не проверяет.

### Builtins

`print(...)`:

- вычисляет все аргументы;
- преобразует их в текст;
- объединяет одним пробелом;
- печатает строку и newline;
- возвращает `Unit`.

`warn.log(...)` печатает `[WARN] ` плюс аргументы.

`error.log(...)` печатает `[ERROR] ` плюс аргументы.

## Что изменилось в native backend

Новая реализация не пытается буквально перенести старый `HashMap + AST interpreter` на C. Она оставляет тот же язык и большую часть семантики, но меняет механизм исполнения.

Новый pipeline:

`RBL -> lexer -> parser -> AST -> C codegen -> GCC/Clang -> native machine code`

### Variables -> slots

Старый runtime:

`HashMap<String, Value>`

Новый runtime:

`Slot slots[N]`

Имя переменной превращается в номер слота уже во время компиляции. Runtime всё ещё хранит `bound` и `Value`, поэтому динамическая семантика `set/let` сохраняется.

Преимущество — из горячего пути убраны строковый hash lookup и AST-поиск имени.

### Expressions -> C temporaries

Вместо:

`eval_expr(AST node)`

генератор создаёт обычные C temporaries:

```text
left
right
result = operation(left, right)
```

Это оставляет порядок evaluation явным и позволяет GCC/Clang оптимизировать код.

### Function dispatch

Чтобы не менять наблюдаемую семантику необязательных/неразрешимых вызовов, backend сначала делает runtime resolve имени и арности, а только потом вычисляет аргументы.

Так сохраняется важная особенность старого интерпретатора: ошибка arity возникает до вычисления аргументов.

### Strings

Строки immutable для RBL runtime. Первый backend использует общий список выделенных строк и освобождает их при завершении процесса. Это проще, чем протаскивать ownership через каждый generated temporary, и при этом проходит ASan leak check.

### Integer overflow

Для integer arithmetic backend использует checked helpers. Это ближе к поведению `cargo run`/debug-режима исходного Rust runtime, чем голый C overflow.

Проверяются add/sub/mul/neg/div, а также overflow в range endpoint `end - 1` и increment loop variable.

## Что проверено

Собраны regression-тесты для:

- арифметики и приоритетов;
- float;
- string concatenation;
- bool и equality;
- `if/elif/else`;
- exclusive/inclusive ranges;
- функций;
- рекурсии;
- Unit;
- `set`/`let` timing;
- non-short-circuit `and/or`;
- side-effect evaluation order;
- проверки арности до evaluation аргументов;
- duplicate function names;
- Unicode identifiers;
- методов `warn.log`/`error.log`.

Отдельно проверено:

- GCC build;
- Clang build;
- генерация Intel x86-64 assembly;
- запуск generated executable;
- AddressSanitizer + UndefinedBehaviorSanitizer;
- полный regression suite.

## Ограничение проверки старого runtime

В текущем контейнере не установлен Rust toolchain (`cargo`/`rustc`), поэтому старый Rust RBL не удалось запустить side-by-side непосредственно здесь.

Поэтому совместимость сейчас проверялась по исходному коду старого runtime и целевым golden/regression-тестам. Для следующего шага полезнее всего будет заморозить старый Rust интерпретатор как oracle и сделать автоматический differential runner `old_rbl == native_rbl` на тысячах сгенерированных программ. (Частично сделано: `tests/differential.py` уже сравнивает два бэкенда — Linux ASM-рантайм и Windows C-рантайм — байт в байт на всём корпусе программ; сравнение с замороженным Rust-интерпретатором остаётся открытым.)

## Что логично делать дальше

Следующая архитектурная ступень — не писать вручную тысячи строк x86-64 для lexer/parser/runtime, а сначала ввести собственный компактный IR RBL.

Тогда pipeline станет:

`RBL -> AST -> RBL IR -> x86-64 backend`

и уже этот backend можно сделать полностью assembly/native без GCC в качестве финального code generator.
