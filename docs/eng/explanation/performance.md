## Explanation: RBL performance

Measurements describe specific programs in a specific environment. They are not a universal language ranking: backend, optimizer, startup cost, algorithm, libraries and execution environment all affect the result.

## Two different benchmark suites

1. `benchmarks/run_benchmarks.py` measures RBL only: build time, total process runtime, startup-adjusted net time and executable size. It works through the active backend.
2. `benchmarks/compare_all.py` compares five implementations of the same synthetic workloads: RBL, C `-O2`, C++ `-O2`, CPython and handwritten x86-64 assembly. It runs on Linux/WSL because the assembly baseline uses Linux syscalls.

See the [benchmarking how-to](../how-to/benchmarking.md) for execution details and [`benchmarks/RESULTS.md`](../../../benchmarks/RESULTS.md) for the current RBL 0.8.0 ten-sample runtime measurement. The run was CPU-pinned but took place while a separate RENA training process was active; its background-load caveat is recorded with the results.

The separate [compiler performance audit](../../../benchmarks/PERFORMANCE_AUDIT.md) isolates the cost of translation-unit boundaries, measures parallel/incremental builds and profiles compiler hot paths. Those figures must not be confused with the runtime benchmark results: they measure the compiler itself, not the generated program.

## Reading the results

- RBL executes native x86-64 code generated by the compiler; it does not interpret an AST.
- CPython pays for Python bytecode interpretation and dynamic operations in these loops. This explains the large gap in these particular workloads, but does not generalize to every Python application or C extension.
- C/C++ use GCC/G++ `-O2`; the optimizer can change the shape of an algorithmic loop while preserving its result.
- Handwritten assembly is a specialized lower bound for these exact small tasks, not an equivalent to an optimal compiler for arbitrary code.
- Full process startup is included in every timed sample. For short programs, startup overhead is significant; RBL build time is reported separately.

## Where further improvements may come from

The current compiler has specialized integer/Boolean fast paths and limited loop-local register allocation, but no general IR/CFG optimizer or global register allocator. The next architectural step is to define an IR and control-flow representation, then add optimizations with regression tests rather than introducing unsafe fast paths without type/control-flow proofs.

## Reproducibility

Every new benchmark result should include the exact benchmark code revision, CPU, OS/kernel, compiler/linker versions, warmups, timed repetitions, raw samples and backend. Update the results table only after rerunning the measurement with the current sources.
