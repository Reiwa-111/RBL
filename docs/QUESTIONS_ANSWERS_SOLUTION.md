# RBL Studio: вопросы → ответы → решение

## Вопросы

### 1. Почему вообще переписывать исполнение RBL?

Текущая Rust-реализация — интерпретатор AST. Он прост и удобен для развития языка, но каждый запуск проходит через обход AST, hash map окружения и динамические проверки. Для экспериментов с производительностью это естественный потолок.

### 2. Что значит «именно ASM», а не очередной C-wrapper?

Нужно, чтобы компилятор RBL выдавал настоящий x86-64 assembly. Пользовательская программа после этого проходит только через assembler и linker: `RBL → .s → .o → ELF`. C-код для пользовательской программы не генерируется, GCC не нужен для её сборки. (В нативном Windows-режиме, добавленном позже, тот же принцип сохранён: генерируется чистый ASM, а MinGW `gcc` используется только как драйвер линковки и для сборки объекта рантайма `runtime/rbl_runtime_win.c`; см. `docs/WINDOWS.md`.)

### 3. Можно ли сохранить семантику старого RBL?

Да. Parser/lexer сохраняют текущую грамматику, а backend повторяет наблюдаемое поведение интерпретатора: порядок вычисления, `set`/`let`, динамические типы, неполное короткое замыкание, области переменных, диапазоны, функции и `Unit`.

### 4. А как запускать это на Windows?

Первый прямой backend — Linux x86-64 / System V ABI. RBL Studio автоматически использует WSL, когда он доступен. То есть Windows остаётся основной средой IDE, а native execution выполняется через Linux ABI в WSL.

### 5. Нужна ли установка отдельного редактора?

Нет. IDE написана на Python + Tkinter без сторонних Python-зависимостей. На Windows запуск — `RBLStudio.cmd`, на Linux — `RBLStudio.sh`.

### 6. Как сделать `.rbl` нормальным типом файла?

В архиве есть Windows installer, который регистрирует ProgID `Reiwa.RBLStudio.RBL`, и Linux MIME/desktop-файлы. После регистрации двойной клик по `.rbl` открывает RBL Studio, а не диалог «неизвестный тип файла».

### 7. Где тесты и скорость?

IDE содержит отдельные Run/Test/Benchmark панели. Regression suite запускает все семантические cases. Benchmark suite отдельно измеряет время native executable и время сборки.

## Ответы

Архитектура разделена на четыре независимых слоя:

```text
RBL source
   │
   ├── lexer
   ├── recursive-descent parser
   └── AST
          │
          ▼
   direct x86-64 codegen
          │
          ├── generated .s
          └── runtime/rbl_runtime.s
                    │
                    ▼
             GNU as --64
                    │
                    ▼
                 ld + libc
                    │
                    ▼
                  ELF
```

Assembler/linker — это инфраструктура генерации машинного кода, а не промежуточный C-компилятор. `gcc` нигде не участвует в сборке пользовательского RBL executable.

## Решение

RBL Studio объединяет всё в один цикл:

1. Открываешь `.rbl` двойным кликом.
2. Редактор сразу подсвечивает синтаксис и показывает номера строк.
3. После паузы в редактировании IDE запускает syntax check.
4. `F5` сохраняет файл, генерирует ASM, собирает ELF и запускает его.
5. Нижняя консоль показывает stdout/stderr.
6. `Build ASM` оставляет сгенерированный `.s` для изучения.
7. `Tests` запускает 57 regression case (плюс отдельный smoke-тест stdlib/input и дифференциальный прогон двух бэкендов).
8. `Bench` запускает три контролируемых benchmark case и показывает build/run/size.
9. Settings хранят тему, размер шрифта, tab size, WSL mode, авто-check, авто-save и номера строк.

### Почему не делать всё на ASM

Сам RBL compiler frontend в этом релизе намеренно остаётся на C: lexer/parser/AST — это удобный и маленький bootstrap-компилятор. **Target backend и runtime — ASM.** Переписывание самого lexer/parser в ASM не ускорило бы программы RBL и резко ухудшило бы поддерживаемость. Это разделение позволяет позже заменить frontend на Rust/C++/сам RBL без изменения ABI.
