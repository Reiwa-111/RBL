## Explanation: производительность RBL

Измерения показывают скорость конкретных программ в конкретной среде. Они не образуют универсального рейтинга языков: backend, оптимизатор, startup, алгоритм, библиотеки и среда выполнения влияют на результат.

## Два разных benchmark набора

1. `benchmarks/run_benchmarks.py` измеряет только RBL: сборку, полное время запуска, startup-adjusted net и размер исполняемого файла. Он поддерживает активный backend.
2. `benchmarks/compare_all.py` сопоставляет пять реализаций одинаковых синтетических workloads: RBL, C `-O2`, C++ `-O2`, CPython и handwritten x86-64 ASM. Запускается на Linux/WSL из-за Linux syscalls в ASM baseline.

Детали запуска и рекомендации — в [how-to benchmark](../how-to/benchmarking.md). В [`benchmarks/RESULTS.md`](../../../benchmarks/RESULTS.md) приведено текущее десятисерийное runtime-измерение RBL 0.8.0. Финальный запуск был привязан к одному CPU, но выполнялся во время обучения RENA; ограничение фоновой нагрузки указано рядом с результатами.

Отдельный [performance-аудит компилятора](../../../benchmarks/PERFORMANCE_AUDIT.md) изолирует стоимость translation-unit boundaries, проверяет параллельную/инкрементальную сборку и профилирует hot paths. Эти значения нельзя смешивать с runtime benchmark: они измеряют сам компилятор, а не сгенерированную программу.

## Как читать результаты

- RBL выполняет сгенерированный компилятором native x86-64 код, а не интерпретирует AST.
- CPython в этих циклах платит за интерпретацию Python bytecode и динамические операции. Это объясняет большой разрыв в этих конкретных workloads, но не переносится на все Python-приложения и C extensions.
- C/C++ собраны с `-O2`; оптимизатор способен менять форму алгоритмического цикла, пока сохраняется результат.
- Handwritten assembly — специализированная нижняя граница для именно этих небольших задач, а не эквивалент оптимального компилятора для любого кода.
- Замер включает полное время запуска процесса. Для коротких программ startup overhead заметен; сборка RBL выводится отдельно.

## Где искать потенциал улучшения

Текущий compiler имеет специализированные integer/boolean fast paths и ограниченную loop-local register allocation, но не имеет общего IR/CFG optimizer и global register allocator. Следующий архитектурный шаг — выделить IR и control flow, затем внедрять оптимизации с regression tests, а не добавлять unsafe fast paths без доказательства типов и управления потоком.

## Воспроизводимость

Каждый новый benchmark result должен включать точную ревизию кода benchmark, CPU, OS/kernel, compiler/linker versions, warmups, timed repetitions, сырые выборки и backend. Обновляйте таблицу после повторного измерения на текущих исходниках.
