## Диагностика компилятора RBL

В RBL 0.8.0 компилятор сохраняет исходные позиции от лексического анализа через parsing и semantic validation до генерации assembly. Позиция содержит исходный файл, byte offset и координаты строки/столбца с нумерацией от единицы.

## Формат диагностики

```text
path/to/program.rbl:12:9: error [parser]: expected TOK_RPAREN, found TOK_EOF
  12 |     print(value
     |         ^
```

Позиция указывает на токен или символ, вызвавший ошибку. Компилятор печатает соответствующую строку исходника и каретку под позицией. Parser errors из-за неожиданного EOF и незакрытые строковые литералы указывают на позицию сразу после последнего символа. Незакрытая интерполяция f-string указывает на открывающую `{`, чтобы показать конструкцию, для которой не нашлась закрывающая скобка.

Метка этапа показывает, где обнаружена ошибка:

| Этап | Ответственность |
|---|---|
| `lexer` | Некорректный UTF-8/NUL input, недопустимые символы, числовые литералы, string escapes и незакрытые литералы |
| `parser` | Неожиданные токены, пропущенные разделители, некорректные выражения, синтаксис f-string, неизвестные namespaces и compile-time constants |
| `semantic` | Некорректный loop control flow, повторные имена параметров и отсутствие функции `main` |
| `codegen` | Ограничения, обнаруживаемые при lowering вызовов и выражений, например неверное число аргументов builtin |

## Правила координат

- Byte offsets внутри компилятора начинаются с нуля и относятся к исходному UTF-8 буферу.
- Номера строк и столбцов начинаются с единицы.
- Столбцы считают Unicode code points, а не UTF-8 bytes. Многобайтовый символ увеличивает столбец на единицу.
- Столбцы не являются количеством grapheme clusters или реальной шириной символов в терминале. Combining marks и широкие восточноазиатские символы могут визуально смещать caret в некоторых терминалах, хотя номер code-point column остаётся последовательным.
- Tab увеличивает логический номер столбца на единицу. В напечатанном фрагменте tab раскрывается до следующей позиции табуляции с шагом четыре столбца, чтобы каретка была видна и правильно выровнена.
- LF, CRLF и одиночный CR дают одинаковые координаты строк/столбцов.
- Встроенный NUL byte в исходном файле отклоняется до запуска lexer вместо незаметного усечения входа; в source excerpt он отображается как `\0`.
- Некорректный UTF-8 (неверные continuation bytes, overlong encodings, surrogate encodings, code points вне диапазона и оборванные последовательности) отклоняется до токенизации; неверные байты экранируются в source excerpt.
- Выражения внутри f-string повторно лексируются, но их координаты переводятся обратно в исходный файл и исходные offsets, а не остаются относительными к временному фрагменту.

Узлы `Expr`, `Stmt`, `Param` и `Function` сохраняют исходный `SourcePos`. Синтетические AST-узлы, создаваемые при desugaring синтаксиса, наследуют позицию исходной конструкции.

## Семантическая проверка

Semantic validation запускается после parsing и до codegen. Сейчас она проверяет:

- `break` и `continue` находятся внутри цикла `for`, в том числе во вложенных `if`;
- имя параметра не объявлено повторно в одной функции;
- программа содержит функцию `main`.

Semantic pass не является общей проверкой имён и типов. Проверки типов аргументов и большинство unresolved dynamic names сохраняют существующее runtime-поведение; неизвестные namespaces и compile-time constants отклоняются parser, а некоторые нарушения инвариантов fast path могут обнаруживаться codegen. Runtime diagnostics в общем случае не привязаны к исходным позициям.

Ошибки до загрузки исходника (file I/O, CLI options, создание временного файла), а также внутренние ошибки allocation/capacity/invariant — инфраструктурные, а не source diagnostics; у них может не быть исходной позиции и excerpt.

## Команды тестирования

```bash
python3 tests/test_diagnostics.py
python3 rbl.py test
```

Набор из 63 сценариев состоит из 45 ошибок исходника, 8 корректных control cases, 4 ожидаемых runtime errors и 6 тестов некорректных UTF-8 byte sequences. Он проверяет позиции lexer, parser, semantic и codegen, выравнивание caret по terminal cells (включая широкие CJK/emoji glyphs и combining marks нулевой ширины), Unicode source columns для двух-, трёх- и четырёхбайтовых UTF-8 символов, tabs, LF/CRLF/CR и EOF, numeric separators, некорректные Unicode escapes, embedded NUL, классы некорректного UTF-8 (continuation, overlong, surrogate, out-of-range и truncated sequences), незакрытые литералы, многострочные строки, вложенные f-string expressions и комментарии внутри интерполяций, грамматику и ограничения format specs, явное отклонение dynamic/nested specs в начале и после width, корректный разбор форматов, включая fill-символы, совпадающие с alignment-символами, runtime type mismatches, ошибки точности для integer и недопустимое сочетание точности с `s`, ошибки namespace/constant и builtin arity. Отдельно проверяется некорректный UTF-8 после корректного многобайтового символа. Source columns по-прежнему считают Unicode code points; ширина caret — приближение типичного terminal rendering, а не гарантия для всех grapheme clusters и терминалов. Проверки выполняются через активный native Windows, WSL или Linux backend. На Windows команда `python tests/differential_diagnostics.py` сравнивает 30 representative diagnostic и valid-source cases между WSL и native Windows после нормализации путей.
